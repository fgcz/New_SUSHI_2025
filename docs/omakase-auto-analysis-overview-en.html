OMAKASE — automated first-pass analysis of finished sequencing orders

System configuration, illustrated — for team discussion. Codename OMAKASE ("chef's choice": the facility proposes the analysis; the customer does not have to order it).

Version v0.3 (illustrated) Date 2026-07-31 (review incorporated) Status configuration sketch — no implementation design yet Full text docs/omakase-auto-analysis-design.md

The original idea is kept as it stands: propose → notify → auto-start if there is no reply → an AI checks the result → a human forwards it to the customer, with everything gated through a bioinformatician in phase 1.
This document exists to settle one question first: which layer does what, and who owns it.

Fig 2Component map — only one thing is new

Only one thing is built

The omakase-core daemon. Dropping the consent dialog also removed the second new item v0.2 needed — a consent field in B-Fabric.

Jobs are always submitted through the SUSHI backend REST API. That gives us project-scope enforcement, the required_params gate, SAMPLE-mode fan-out and legacy-parity output columns for free — and it means no code path exists by which the orchestrator could corrupt the shared production database.

Fig 3Data minimisation — no consent dialog

Rather than asking permission to process sensitive data, we never read it.
To decide which pipeline to run we only need non-sensitive order parameters.

Three rules

  • Allow-list, not redaction. Only listed fields are fetched. What is never fetched cannot leak through a bug in a scrubber.
  • Local vLLM only. No institutional cloud, no hosted API. The whole "which tool is approved for which classification" matrix disappears from the design.
  • No raw data and no free-text logs. QC sends numbers, which is what the deterministic checks work on anyway.
The one caveat to keep in view

Data minimisation removes the consent question only while the payload stays inside the allow-list. The moment someone wants to send log text or result tables, the question comes back.

So the allow-list is a security boundary: enforced in code, and reviewed when it changes.

Fig 4LLM channel — one, on-premises

Point the local provider of llm_client (OpenAI-compatible) at the FGCZ vLLM. That is the only channel used. Schema-constrained output (output_schema) is already supported.

The guard becomes small

Because the channel is fixed and the payload is allow-listed, the check in front of llm_client is just two questions. Is every field on the allow-list? Is the endpoint the local one? Otherwise refuse, and log it.

Fig 5QC — reuse loop_validation as it is

The existing verification discipline loop_validation in SUSHI-MCP-server already says what we need:

"The acting LLM's self-report is never evidence. A verdict consumes only mechanically observable results, and absence of evidence never defaults to a pass."

So the QC gate is an instance of it. We do not build a new QC framework.

Architecture

Agreed that the always-on layer is plain code, with the LLM and the harness invoked per event?

Agreed that the AI triage agent is started by a human only in phase 1?

Agreed to start without a consent dialog — allow-listed parameters, on-prem model, plain notice?

Agreed to standardise on one LLM service for ezRun / SAKE / OMAKASE?

The number of places that call an LLM is growing

The M&M module in ezRun, method-description generation in SAKE, and OMAKASE would be a third. If every module keeps its own caller, maintenance cost grows with each one.

A shared library is not possible here: ezRun is R, SUSHI-MCP-server is Ruby, omakase-core would be Python. Only a service can be shared. Deciding on one before the third exists is the cheap moment.
