OMAKASE — automated first-pass analysis of finished sequencing orders

System configuration, illustrated — for team discussion. Codename OMAKASE ("chef's choice": the facility proposes the analysis; the customer does not have to order it).

Version v0.3 (illustrated) Date 2026-07-31 (review incorporated) Status configuration sketch — no implementation design yet Full text docs/omakase-auto-analysis-design.md

The original idea is kept as it stands: propose → notify → auto-start if there is no reply → an AI checks the result → a human forwards it to the customer, with everything gated through a bioinformatician in phase 1.
This document exists to settle one question first: which layer does what, and who owns it.

Fig 2Component map — only one thing is new

Only one thing is built

The omakase-core daemon. Dropping the consent dialog also removed the second new item v0.2 needed — a consent field in B-Fabric.

Jobs are always submitted through the SUSHI backend REST API. That gives us project-scope enforcement, the required_params gate, SAMPLE-mode fan-out and legacy-parity output columns for free — and it means no code path exists by which the orchestrator could corrupt the shared production database.

Fig 3Data minimisation — no consent dialog

Rather than asking permission to process sensitive data, we never read it.
To decide which pipeline to run we only need non-sensitive order parameters.

Three rules

  • Allow-list, not redaction. Only listed fields are fetched. What is never fetched cannot leak through a bug in a scrubber.
  • Local vLLM only. No institutional cloud, no hosted API. The whole "which tool is approved for which classification" matrix disappears from the design.
  • No raw data and no free-text logs. QC sends numbers, which is what the deterministic checks work on anyway.
The one caveat to keep in view

Data minimisation removes the consent question only while the payload stays inside the allow-list. The moment someone wants to send log text or result tables, the question comes back.

So the allow-list is a security boundary: enforced in code, and reviewed when it changes.

Fig 4Determinism — why the LLM is safe to use here

There are two axes to close, and they close separately. Data — what the AI may see — was closed by the allow-list in Fig 3. What remains is authority — what the AI may decide. That one is closed by letting it decide nothing binding.

What reproducibility buys — four properties

1. Bounded blast radius

The worst an LLM error can do is pick the wrong recipe among reviewed recipes (caught by the veto window) or write a poor sentence (caught by the human release gate).

It cannot invent an unreviewed pipeline, and the REST API refuses an unresolved parameter before submission.

2. The model is not on the critical path

If the on-prem model is down, the rule engine still proposes. The availability of an LLM never becomes the availability of the service.

3. Behaviour change is reviewable

Changing what runs is a diff in a versioned recipe, with an author. It is not an edited prompt.

4. Incidents are answerable

“Why was this analysis run?” is answered with recipe_id@version and its author — not with “the model chose it”.

The honest limit

Determinism does not make the recipes correct. It makes them reviewable, testable and attributable. Correctness comes from a bioinformatician authoring the recipe, and from the Tier-3 history comparison (Fig 7).

Concretely: unresolved ref_selector values once reached SLURM and polluted output rows across 13 of 16 allow-listed apps, until the required_params gate landed. A deterministic path does not produce that class of failure.

The guard becomes small

Because the channel is fixed and the payload is allow-listed, the check in front of llm_client is just two questions. Is every field on the allow-list? Is the endpoint the local one? Otherwise refuse, and log it.

Fig 6Skills — they tune how the AI works, not what runs

A Skill here means a curated, versioned unit of instruction and knowledge that an agent loads at run time from SUSHI-MCP-server. It is the natural place to encode how the AI should investigate and explain, and the wrong place to encode what gets run.

The boundary rule

Skills tune how the AI investigates and words things. They never change which analysis runs, and they never change a QC threshold.

One honest caveat

A Skill is a prompt with provenance. It improves consistency and makes behaviour attributable; it does not turn the agent's conclusions into evidence.

That is why triage output is advisory, and why the mechanical verdict of loop_validation (Fig 7) sits underneath it.

Fig 7QC — reuse loop_validation as it is

The existing verification discipline loop_validation in SUSHI-MCP-server already says what we need:

"The acting LLM's self-report is never evidence. A verdict consumes only mechanically observable results, and absence of evidence never defaults to a pass."

So the QC gate is an instance of it. We do not build a new QC framework.

Fig 11A chat surface — solving “will anyone notice in time?”

The three channels — B-Fabric comment, email digest, MCP tools — answer “can a human act at all?”. A chat bot answers a different question: will a human notice in time? That is the weakest point of the whole gate. An unread comment or a filtered digest mail makes the veto window ceremonial.

A bot fits here precisely because it decides nothing. It reports state the state machine already holds, and relays actions into the same audited transitions the CLI uses.

When the bot posts, and what
WhenWhat it posts
Every morningProposals awaiting a response with their deadline countdown; jobs finished or failed since yesterday; QC WARN / FAIL waiting for review
On a new proposalOrder, recipe, resolved parameters, cost estimate, deadline — with veto and hold affordances
One hour before a deadlineA reminder naming the person expected to act
On failure or QC FAILThe job and its state, plus the diagnosis if triage has run
On demand“status of order X”, “what is pending for p35611”, “why did job 581 fail”

Business-hours deadlines are already computed by the daemon, so the bot can say “two proposals expire before 18:00 today”. Each alert becomes a thread, and the thread is the working context: a veto reason typed in the thread is the reason recorded in the transition log.

Constraints, and the order to build in

Write actions are an authorisation surface. A chat identity must map to an LDAP login before it can act. Recommended split for phase 1: read, veto and hold from chat; override and release to the customer from the CLI, or from chat only behind an explicit confirmation. Releasing a result to a customer is a bigger step than stopping a job.

The bot is never the source of truth. It reads state through the same API the CLI uses, and every action it relays lands in the transitions table with the resolved LDAP actor — not “slack-bot”.

Alert fatigue is the failure mode. One post per state transition, digests instead of per-event mail, per-person routing, no re-posting. If the response rate drops, the gate is theatre again — so response rate is worth tracking as a health metric.

Build order. An outgoing webhook that posts the morning digest is roughly a day of work, has no inbound surface and no auth surface, and already delivers most of the value. Interactive buttons come next, the conversational tier after that — and only once the identity mapping exists.

Architecture

Agreed to start without a consent dialog — allow-listed parameters, on-prem model, plain notice?

Agreed to standardise on one LLM service for ezRun / SAKE / OMAKASE?

The number of places that call an LLM is growing

The M&M module in ezRun, method-description generation in SAKE, and OMAKASE would be a third. If every module keeps its own caller, maintenance cost grows with each one.

A shared library is not possible here: ezRun is R, SUSHI-MCP-server is Ruby, omakase-core would be Python. Only a service can be shared. Deciding on one before the third exists is the cheap moment.
