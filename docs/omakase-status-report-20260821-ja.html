1OMAKASE とは何か、7つの層

受注の配列解析が終わったら、規則（言語モデルではなく）が一次解析を選び、 バイオインフォマティシャンが承認し、既存の SUSHI のジョブ経路で実行する。 結果の健全性を機械が判定し、人が顧客に渡す。合言葉は 「規則が決める・AI は助ける・人が出す」です。

作るものは1つだけ

新規開発は omakase-core（自前の状態データベースを持つ Python の常駐プロセス）だけです。 SUSHI のスキーマは変更しません。SUSHI への変更はすべて REST API 経由で、 データベースを直接書く経路は作りません。

2ここまでの進み方

合意した順番は A → B → C → D です。A と B は終わり、B の途中で必要になった 実測（B2）も終わりました。

3測ってわかった一番大事なこと

入口は2つあります。B-Fabric の受注情報と、SUSHI に納品されたデータセットです。 両方を本番で実測しました。読み取りのみ、言語モデルは使わず、出力は集計値だけです。 そして両方の欠損が、同じ1つのサービス種別に集まっていました。

これが今回の一番の収穫です

「メタデータの質が悪い」という漠然とした話が、「1つのサービス種別の1つの項目」という 具体的な依頼に変わりました。しかもその種別は、FGCZ が調製していないライブラリ （顧客が作って持ち込むもの）なので、顧客は答えを知っています。

5Species はどこから来るのか

設計では Species を受注情報から読む前提でしたが、受注情報に Species という項目は存在しません。 本番で確認しました。受注は49項目、サンプルは13項目を返しますが、種・生物種・分類・株に当たるものは1つもありません。 Species はSUSHI のデータセットの列で、つまりデータが納品されてから初めて存在します。

設計を1つ楽にした発見

/srv/GT/reference-favorite は、種ごとの推奨ゲノムを人が保守している表です。 ヒト・マウス・ラット・イヌ・シロイヌナズナの5種。SUSHI の画面で参照ゲノムを選ぶとき、 一番上に出てくるのがこれです。つまり「種から参照ゲノムを決める方針」を OMAKASE が 発明する必要はなく、発明してはいけません。その判断には既に持ち主がいます。 この5種で、種名が具体的に書かれている 836 件のうち 712 件（85.2%）を覆います。

Species を読むのは追加コストではない

許可リストに載っている18個のアプリのうち13個が Species を必須列として宣言しています。 つまり実行する側は、どんなトリガーであれデータセットを読まないとジョブを作れません。 「データセットも読む」という選択は、すでに払っているコストです。

「別名の承認が必要」を別枠にしてあるのは意図的です。Human と Homo_sapiens が同じ、というのは生物学上の主張であって、機械が勝手に決めてよいものでは ありません。だから 51.7% という見出しの数字には、こちらが推測で作った同一性判断が1つも 入っていません。Escherichia coli K12 はカタログに3つの株があるので、あえて未解決のまま 残してあります。

7いま出ている依頼と、その根拠

「メタデータをもっと正確に」という以前の口頭依頼を、数字付きの文書に置き換えました （docs/omakase-bfabric-metadata-request.md、下書き・未送付）。3つの依頼はすべて 同じ1つのサービス種別に向いています。

綴り間違いは、規則を書く側から見ると特に厄介です。誰もその綴りで規則を書かないので、 11 件が静かに漏れます。こちら側でも正規化して二重に守ります。

9次にやること

判断待ちで止まっているものはありません。残っているのは 設計 §17 のステップ2、レシピを書く作業です。

次の作業誰が状態
レシピを書く — 準備度が 100% に近い種別から（NGS、Single Cell、Spatial、Long Read、ONT）バイオインフォマティシャンここが本体。過去のジョブから機械的に導くことは、設計で明示的に否定済み
レシピの形式・読み込み・条件判定の仕組み。提案を見せる前にアプリの設定と突き合わせて検証する部分実装側レシピ本体と独立に作れる
Sequencing Application の表記ゆれ正規化（重複5組）実装側仕様は依頼書に記載済み。実装先はレシピの判定部分
C. 人が同席する試作（推論部分のみ）実装側Python から直接オンプレのモデルを呼ぶ方針で、依存問題を回避できる
依頼書の送付依頼元の判断下書きのまま。送っていません
エージェント本体のプロトタイプ（hermes-agent）を skillset にするか別トラックOMAKASE の必須経路から外すことは決定済み。skillset 化そのものは未決で、別セッションでレビュー中
レシピについての約束事

レシピ集と QC の判定基準は最初から人が手で書くものとし、エージェントに生成させません。 ここを崩すと、後から決定論的な中核（omakase-core）を切り出すことができなくなります。 レシピ集はそれ自体に価値があります — 受注種別ごとの「現在のベストプラクティス」を 機械が読める形にした最初の記録になります。

他の人に預けてある確認事項

  • B-Fabric のどの項目を見れば「新しいデータが gStore に届いた」とわかるか。 項目名、値、そして実際にファイルが置かれてから B-Fabric に現れるまでの遅れ。 これがトリガーの形を決めます。
  • コメントを職員だけに見せられるか、どの単位（受注／コンテナ／作業単位）で可能か。 第1段階のゲートの形がこれで決まります。
  • 読み取り用のサービスアカウントを使えるか。
  • 顧客に出す一文「実験パラメータはローカルの AI モデルで処理されます」の文面と置き場所を誰が決めるか。
