OMAKASE — 受注シーケンスの自動一次解析

全体構成の図解（チーム検討用）／ コード名 OMAKASE ＝「お任せ」：顧客が注文しなくても施設側が解析を提案する

元のアイデア（提案 → 通知 → 4時間無応答で自動開始 → 完了後にAIが整合性確認 → 人が顧客へ転送、 Phase 1は必ず bioinformatician を経由）はそのまま採用しています。

図2コンポーネント配置 ── 新規は1つだけ

作るものは1つだけ

omakase-core（Python デーモン）。同意ダイアログを外したので、v0.2 で必要だった B-Fabric 側の新規フィールドも不要になりました。

ジョブ投入は必ず SUSHI backend の REST 経由にします。これで project スコープ強制・required_params ゲート・SAMPLE 分岐・legacy 互換の出力カラムが自動的に付いてきて、共有本番DBを壊す経路が存在しなくなります。

図3データ最小化 ── 同意ダイアログを置かない

センシティブなデータの利用許可を求めるのではなく、そもそも読み込まないという設計です。
どのパイプラインを選ぶかを決めるのに必要なのは、機密性のないオーダー項目だけです。

3つのルール

  • マスクではなく許可リスト。リストにある項目しか取得しません。取得しなければ、スクラバのバグで漏れることもありません。
  • ローカル vLLM のみ。機関クラウドもホスト API も使いません。「どのツールがどの分類まで許されるか」という表が設計から消えます。
  • raw data とフリーテキストのログは渡さない。QC が渡すのは数値メトリクスだけです。決定論的なチェックはもともと数値で動きます。
残る注意点

データ最小化が同意の問題を消すのは、送信内容が許可リストの内側にとどまる限りです。あとからログ本文や結果テーブルを渡したくなった時点で、問題は戻ってきます。

したがって許可リストはセキュリティ境界です。コードで強制し、変更はレビュー対象にします。

図4決定論 ── LLM を安全に使えている理由

閉じるべき軸は2つあり、別々に閉じます。データ（AI に何を見せるか）は図3の許可リストで閉じました。 残るのは権限（AI に何を決めさせるか）です。こちらは「拘束力のある決定を一切させない」で閉じます。

再現性が買っているもの ── 4つの性質

① 影響範囲が限定される

LLM が間違えても、起きるのはレビュー済み recipe の中での選び違え（veto の窓で捕まる）か、下手な文章（人のリリース判断で捕まる）だけです。

未レビューのパイプラインは作れません。未解決のパラメータは REST API が投入前に弾きます。

② モデルが臨界経路に乗らない

オンプレ LLM が落ちていても、ルールエンジンは提案を出せます。LLM の可用性が、サービスの可用性になりません。

③ 挙動の変更がレビューできる

「何が走るか」を変えるのは、版管理された recipe の diff と、その作成者です。プロンプトの書き換えではありません。

④ 事故を説明できる

「なぜこの解析が走ったのか」に、recipe_id@version とその作成者で答えられます。「モデルが選びました」ではありません。

何を誰が決めるか
決めること決めるものLLM の役割

正直な限界

決定論は recipe が正しいことを保証しません。レビューでき、テストでき、誰の判断か辿れる状態にするだけです。正しさは、担当 bioinformatician が recipe を書くことと、Tier 3 の履歴比較（図7）から来ます。

効き目の実例：未解決の ref_selector 値がそのまま SLURM に渡り、許可 16 app のうち 13 で出力行を汚した事例がありました（required_params ゲートで解消済み）。決定論的な経路では、この種の失敗は構造的に起きません。

図5LLM チャネル ── オンプレの1本だけ

llm_client の local provider（OpenAI 互換）を FGCZ の vLLM に向けます。 使うのはこの1本だけです。型付き出力（output_schema）も既に対応しています。

チャネルが固定で、送信内容が許可リストに限られるため、llm_client の前に置く確認は2つだけです。全項目が許可リストにあるか。宛先がローカルのエンドポイントか。違えば拒否してログに残します。

図6Skills ── 調べ方を調整する。走るものは変えない

ここでいう Skill は、エージェントが実行時に SUSHI-MCP-server から読み込む、版管理された手順と知識のまとまりです。 「AI がどう調べ、どう書くか」を置く場所としては最適で、「何を走らせるか」を置く場所としては最悪です。

境界のルール

Skills は、AI の調べ方と書き方を調整する。どの解析が走るかは変えない。QC の閾値も変えない。

正直な注意

Skill は出所のついたプロンプトです。一貫性は上がり、挙動の由来も辿れるようになりますが、それでエージェントの結論が証拠になるわけではありません。

だから triage の出力は助言どまりで、その下に loop_validation の機械的な判定（図7）が置いてあります。

図7QC ── loop_validation をそのまま適用する

SUSHI-MCP-server の既存の検証規律 loop_validation に、必要なことがすでに書かれています。

「実行 LLM の自己申告は証拠にならない。判定は機械観測可能な結果のみを消費し、証拠の不在は決して pass に倒れない。」

つまり QC ゲートは loop_validation のインスタンスです。新しい QC フレームワークは作りません。

図11チャット面 ── 「期限内に気づくか」を解く

B-Fabric コメント・メール・MCP ツールの3チャネルが解いているのは「人が操作できるか」です。 チャット bot が解くのは別の問いです。人が期限内に気づくか。ゲート全体でここが一番弱い場所です。 読まれないコメントや振り分けられたメールは、veto の窓を形だけのものにします。

bot がこの役に向いているのは、何も決めないからです。状態機械がすでに持っている状態を報告し、 人の操作を CLI と同じ監査経路に流すだけです。

いつ、何を投稿するか
いつ何を投稿するか
毎朝未応答の提案と期限までの残り時間／前日からの完了・失敗／レビュー待ちの QC WARN・FAIL
新しい提案が出たときorder・recipe・解決済みパラメータ・費用見積り・期限。veto と hold の操作を添えて
期限の1時間前対応が期待されている人を名指しでリマインド
失敗・QC FAIL のときジョブと状態。triage を回してあれば原因の見立ても
聞かれたとき「order X の状況」「p35611 で止まっているもの」「job 581 はなぜ失敗したか」

営業時間換算の期限は daemon がすでに計算しているので、bot は「今日の 18:00 までに2件、期限が来ます」と言えます。 アラートは1件ずつスレッドになり、そのスレッドが作業の場になります。スレッドに書いた veto の理由が、そのまま遷移ログに残る理由です。

制約と、作る順番

書き込みは権限の面です。チャット ID を LDAP ログインに対応づけるまで、操作はさせません。Phase 1 の推奨は、read / veto / hold はチャットから、override と顧客へのリリースは CLI から（またはチャットから明示的な確認を挟んで）。結果を顧客に出すのは、ジョブを止めるより大きな一歩です。

bot は真実の源ではありません。CLI と同じ API で状態を読み、操作は必ず transitions 表に LDAP の実行者で残ります。“slack-bot” では残しません。

失敗モードは通知疲れです。1遷移につき1投稿、個別メールではなくダイジェスト、宛先の振り分け、再投稿なし。反応率が落ちればゲートはまた形だけになるので、反応率そのものを健全性の指標として見ます。

作る順番。まず morning digest を webhook で投げるだけのもの（1日程度、受信面も認証面も持たない）。それで価値の大半は出ます。ボタン、次に対話。対話は ID 対応ができてからです。
