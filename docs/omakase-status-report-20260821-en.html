1What OMAKASE is, in seven layers

When sequencing for an order finishes, a rule — not a language model — selects a first-pass analysis, a bioinformatician approves it, and it runs through the existing SUSHI job path. A deterministic check decides whether the result is sane, and a person releases it. The catchphrase is rules decide, AI assists, humans release.

Only one component gets built

The single piece of new development is omakase-core, a plain Python daemon with its own state database. The SUSHI schema is not changed. Every change to SUSHI goes through the REST API, and no path is built that writes the database directly.

2How far the work has come

The agreed order is A → B → C → D. A and B are done, and so is the measurement (B2) that B turned out to require.

3The most important thing the measurements found

There are two entry points: the B-Fabric order record and the dataset delivered into SUSHI. Both were measured against production — read-only, no language model, aggregate output only. Both gaps turned out to sit in the same single service type.

This is the finding that mattered

A vague complaint — "the metadata quality is poor" — became a specific request: one field, on one service type. And in that service type FGCZ did not prepare the library; the customer did, so the customer knows the answer.

5Where Species comes from

The design assumed Species could be read from the order. There is no Species field on the order. Verified against production: the order endpoint returns 49 fields and the sample endpoint 13, and none of them is species, organism, taxon or strain. Species is a column on the SUSHI dataset, so it exists only once data has been delivered.

The finding that made the design smaller

/srv/GT/reference-favorite is a human-maintained table of the recommended build per species — human, mouse, rat, dog and Arabidopsis thaliana. It is what SUSHI already lists at the top of the reference dropdown. So OMAKASE does not need to invent a species-to-build policy, and must not: that decision already has an owner. Those five species cover 712 of the 836 datasets that name a specific species — 85.2%.

Reading Species costs nothing extra

Of the 18 allow-listed apps, 13 declare Species as a required column. The execution layer therefore has to read the dataset before it can build a job, whatever the trigger does. "Also read the dataset" is a cost already being paid.

One note on how the number was built

"Needs an alias signed off" is a separate class on purpose. That Human and Homo_sapiens are the same thing is a claim about biology, not something a machine should decide by itself. So the headline 51.7% contains no identity judgment invented here. Escherichia coli K12 is left unresolved deliberately — the catalog holds three K12 strains, and picking one would be exactly the forbidden move.

7The request that follows, and its evidence

The earlier informal ask — "we need better metadata" — has been replaced by a document with the numbers attached (docs/omakase-bfabric-metadata-request.md, draft, not sent). All three requests point at the same single service type.

RequestWhatWhat it buys

R3Clean up five duplicate entries in the Sequencing Application menu, one of which is a misspelling (Experssion, 11 orders)224 orders stop being ambiguous. Costs nothing but a vocabulary edit

The misspelling is the worst of the three from a rule-writer's point of view: nobody will ever write a rule for that spelling, so 11 orders fall through silently. We normalise on our side as well, so the two defences overlap.

The standing condition on recipes

The recipe catalog and the QC thresholds are hand-written from day one and never generated by an agent. Break that and the deterministic core (omakase-core) can no longer be carved out later. The catalog is also valuable in its own right: it becomes the first machine-readable record of current best practice per order type.

Questions sitting with other people
