— Rules decide · AI assists · Humans release —
FGCZ Genomics · 2026 · Masaomi Hatakeyama · v0.3（構成案・実装は未着手）
背景 · 目的
すべての完了オーダーに一次解析を提案する

元のアイデア

  • シーケンス完了 → エージェントがオーダー情報を読む
  • 解析を提案し、担当 bioinformatician に通知する
  • 猶予時間内に応答がなければ、その解析を開始する
  • 完了後に整合性を確認し、人が結果を顧客へ渡す
  • Phase 1 では、すべて bioinformatician を経由する

この資料で決めること

  • どの層が何を担い、誰が持つか
  • 既存の何を再利用し、本当に新規なのは何か
  • AI に何を見せるか。推論をどこで行うか
  • 実オーダーで動かす前に、どう検証するか
  • 決めないこと：実装。コードはまだ1行も書いていません
設計の前提：価値は「AI が解析を選ぶこと」ではありません。すべてのオーダーに、役に立つ早さで一次解析が付き、かつ人がいつでも止められること、です。

再現性 · 安全性
決定論的にすることが、LLM を安全にする
2つの軸を別々に閉じる。 データ — AI に何を見せるか。項目許可リストで閉じる。  権限 — AI に何を決めさせるか。recipe カタログで閉じる。渡すデータを絞っても、決定をモデルに委ねれば再現できません。
仕事決めるのはLLM の役割
どの app 連鎖を回すかrecipe の判定条件なし
パラメータ（参照ゲノム・cores・ram）recipe ＋ 種 → 参照ゲノム表なし
複数 recipe が該当／該当なしLLM が既存の recipe id から選ぶ。確信度が低ければ人に保留制約付きの選択
提案文・QC 所見文テンプレート ＋ LLM文章を書く
QC の合否実行前に宣言した決定論的な3階層下げることだけ可
失敗の原因調査LLM エージェント（人が起動）本格的なエージェント作業
  • 記録から再現できる — recipe id と版、解決済みパラメータ、入力 dataset、QC 仕様のハッシュ。モデルもプロンプトも温度も seed も関与しません

  • クリティカルパスに乗らない — モデルが使えなくても、ルールが提案します

正直な限界：決定論的にしても recipe が正しくなるわけではありません。レビュー可能・テスト可能・帰属可能になるだけです。正しさは recipe を書く bioinformatician と、同じ recipe の履歴と比較する Tier 3 QC から来ます。

Skill · どこに効かせるか
Skill が調整するのは、AI の働き方。回す内容ではない
Skill とは、エージェントが実行時に読み込む、版管理された指示と知識の単位です。どう調べるか・どう書くかを入れる場所としては正しく、どの解析を回すかを入れる場所としては誤りです。
何を調整するか調整するのは使わないもの
どの解析を回すかrecipe YAML — 作成・レビュー・承認を経るSkill
QC の閾値とチェック内容QC 仕様（recipe と同時に版管理）Skill
失敗をどう診断するかSkill — known errors、app ガイド、デバッグ手順—
所見をどう書くかプロンプトテンプレート—
どのデータをどこへ送れるかコード内の許可リスト。AI 利用ポリシーを基層として併用Skill 単独

Skill が本当に効く場所

  • 失敗の triage — known errors・app 開発ガイド・デバッグ手順を読み込み、ログ・gStore・SLURM を調べる。出力は人への提案で、実行ではありません
  • 検証の規律そのもの — 実行前に evidence spec を宣言し、fail-closed で判定し、仕様のハッシュと共に記録する。QC ゲートはその一実装です
  • 組織のガードレールを基層として — AI 利用ポリシーを Skill として読み込み、全エージェントが継承します
  • 再デプロイなしの調整 — triage の質を上げるのは Skill の編集で、デーモンの変更ではありません

やってはいけない形と、1つの注意

  • Skill の中に解析の選択を書くこと —「RNA-seq なら STAR → FeatureCounts」。動いてしまいますが、設計全体を静かに無効化します
  • 挙動が「どの Skill 版を読んだか」に依存し、記録が自己説明できなくなります
  • Skill は出自付きのプロンプトです。一貫性を上げ、挙動を帰属可能にします。エージェントの結論を証拠に変えるものではありません
  • だから triage の出力は助言に留め、その下に機械的な判定を置きます

L0 · データ最小化
読まないデータの許可は、求めなくてよい
B-Fabric の order レコード 多数の項目を持つ。顧客名・連絡先・課題名・サンプル名・フリーテキストのコメントなど。
→
項目許可リスト（コードで固定） Service Type · Sequencing Application · Species · Instrument · Library Protocol · サンプル数・レイアウト
→
FGCZ ローカルモデル オンプレで推論。FGCZ 網から出ない。外部クラウドは一切使わない。

3つのルール

  • マスクではなく許可リスト — リスト外は取得しない。取得しなければスクラバのバグでも漏れない
  • オンプレのモデルのみ —「どのツールがどの分類まで許されるか」の表が消える
  • raw data とログ本文は渡さない — QC は数値メトリクスのみ。ログにはパスやサンプル名が入る

顧客への説明

  • ダイアログもチェックボックスも置かない。1文で伝える：
  • “Experiment parameters will be processed by a local AI model.”
  • 文面と掲載場所は、顧客向け文書の担当と要確認
残る注意点：これが成り立つのは、送信内容が許可リストの内側にとどまる限りです。許可リストはセキュリティ境界として扱い、コードで強制し、変更はレビュー対象にします。

  • トークンによる project スコープの強制

  • 許可リスト項目に対する判定条件
  • 解決済みパラメータ付きの app 連鎖
  • QC 仕様・計算予算・自動開始フラグ
  • bioinformatician が書き、git で版管理し、実行ごとに recipe_id@version を記録

チャット窓口 · Slack / Teams
veto の時間を守る「秘書」
ここまでの3チャネルは「人が操作できるか」に答えるものです。bot が答えるのは別の問いです。人は間に合うタイミングで気づくか。ゲート全体で最も弱いのがここで、読まれないコメントは veto の時間を形式だけのものにします。

投稿する内容

  • 毎朝 — 応答待ちの提案と期限のカウントダウン。前日以降に完了・失敗したジョブ。レビュー待ちの QC 警告
  • 新しい提案時 — order・recipe・解決済みパラメータ・費用見積・期限。veto と保留の操作を付ける
  • 期限1時間前 — 対応すべき担当者名を添えたリマインド
  • 随時の問い合わせ —「order X の状況」「この project の未処理」「job 581 はなぜ失敗したか」

2層構造 — その境界が統治の境界

  • Tier A・能動 — ダイジェスト、アラート、期限リマインド。素のコードで「状態を引く→整形→投稿」。LLM なし。ただのスケジュール実行なので無人で回せる
  • Tier B・受動 — スレッド内の自由記述の質問に、Skill を参照するエージェントが1メッセージ＝1タスクで答える
  • チャットのメッセージは、人が起動した呼び出しです — 誰かが打ち込み、スレッドで答えを待っています。つまり会話層は構造的に attended であり、他の場面でエージェント利用を止めていた条件をここでは満たします
制約。Slack と Teams は外部クラウドです。モデルと同じ分類の問題が、今度は転送経路について発生します。機関テナントの Teams が安全側の既定で、Slack はポリシー確認が必要です。bot も許可リストを継承します。識別子・状態・期限は投稿してよく、サンプル名や結果の内容は投稿しません。操作を許す前にチャット ID と LDAP ログインの対応付けが必要です。Phase 1 は、閲覧・veto・保留までをチャットから、override と release は CLI から。
作る順番：朝のダイジェストを投げる outgoing webhook は1日程度の作業で、受信口も認証面も持たず、価値の大半を出します。ボタン操作と会話層は、ID 対応付けができてからです。

設計を止めている問いは4つ。あとは詳細

B-Fabric — Falko

  • gStore に新データが来たことを、B-Fabric の何を見れば知れるか。項目・値・遅延
  • スタッフのみに見えるコメントは可能か。どのエンティティか
  • 読み取りとコメント投稿に使えるサービスアカウントはあるか
トリガー層がこれで決まる

メタ情報 — Simon

  • 依頼済み：Service Type / Sequencing Application / Species / Instrument / Library Protocol の精度向上
  • Ready-made library sequencing が “Custom/Other” では判定に使えない
  • どの項目を必須化できるか。いつから

顧客向け文書

  • ローカルモデル利用の説明文、文面と掲載場所。承認者は誰か
  • Phase 2 の顧客向けコメントに AI 起草の明示は必要か。UZH / ETH の透明性規定を読む限り、必要

運用

  • 猶予時間を営業時間換算で確定してよいか
  • パイロット範囲。どのオーダー種、どの project
  • 計算予算・月次上限・低優先キュー（受注ジョブを遅らせないため）
  • 「結果を顧客へ渡す」の具体形
今決めておきたい構成上の1点：LLM を呼ぶ場所は既に複数あります（ezRun の M&M モジュール、SAKE の method description）。R / Ruby / Python にまたがるため共有ライブラリは作れず、共有できるのはサービスだけです。3つ目が生まれる前に1つ決めるのが安いはずです。
