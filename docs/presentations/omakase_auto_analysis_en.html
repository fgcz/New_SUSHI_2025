OMAKASE
Automated first-pass analysis of finished sequencing orders — a configuration proposal
— Rules decide · AI assists · Humans release —
FGCZ Genomics · 2026 · Masaomi Hatakeyama · v0.3 (configuration sketch, no code yet)
Context · Goal
Every finished order gets a proposed analysis

The idea

  • Sequencing finishes → an agent reads the order parameters
  • It proposes an analysis and notifies the bioinformatician
  • No reply within the grace period → the analysis starts
  • After the run, consistency is checked, then a human forwards the result
  • Phase 1: everything gated through a bioinformatician

What this deck settles

  • Which layer does what, and who owns it
  • Which existing components are reused, and what is genuinely new
  • What the AI may see, and where inference happens
  • How we validate before anything runs on real orders
  • Not settled here: implementation. No code has been written.
Design premise: the value is not "an AI that chooses analyses". It is a first-pass analysis for every order, produced early enough to be useful, with a human always able to stop it.

Design · Decisions
Five decisions that shape everything else
D1
No consent dialog. Data minimisation instead.
Only non-sensitive order parameters are read; only the on-prem model is used; the customer is informed, not asked.
D2
A versioned recipe catalog decides. The LLM only assists.
A rule can be reviewed and signed off by a bioinformatician. A prompt cannot.
D3
QC is deterministic first. The LLM writes the wording.
The acting model's self-report is never evidence. Verdict comes from measurements.
D4
The always-on part is plain code, not an LLM.
Watcher, timer and state machine are ordinary software. The model is called per event.
D5
The grace period counts business hours.
And the clock starts only after the notice is confirmed as delivered.
One consequence worth stating: because the decision layer is a rule engine, the service still works when the model is unavailable, or when an order type is deliberately excluded from AI processing.

Reproducibility · Safety
Determinism is what makes the LLM safe
Two axes, closed separately.  Data — what may the AI see? Closed by the field allow-list.   Authority — what may the AI decide? Closed by the recipe catalog. Sending less data does not help if the model still decides what runs.
TaskDecided byLLM role
Which app chain runsrecipe match predicatenone
Parameters (reference, cores, ram)recipe + species → reference tablenone
Several recipes match, or noneLLM picks among existing recipe ids; low confidence → held for a humanconstrained choice
Proposal and QC wordingtemplate + LLMwrites the sentence
QC verdictdeterministic tiers, declared before the runmay only downgrade
Diagnosis of a failureLLM agent, started by a humanfull agentic work
  • Reproducible from the record — recipe id and version, resolved parameters, input dataset, QC spec hash. No model, prompt, temperature or seed is involved
  • Bounded blast radius — the worst an LLM error can do is pick a wrong reviewed recipe, or write a poor sentence. It cannot invent an unreviewed pipeline
  • Never on the critical path — if the model is unavailable, the rules still propose
  • Incidents are answerable — "why was this run?" cites a recipe version and its author, not "the model chose it"
The honest limit: determinism does not make the recipes correct. It makes them reviewable, testable and attributable. Correctness comes from the bioinformatician who authors them, and from Tier-3 QC comparing each run against the history of the same recipe.

Skills · Where they apply
Skills tune how the AI works, not what runs
A Skill is a curated, versioned unit of instruction and knowledge that the agent loads at run time. It is the right container for how to investigate and how to word things — and the wrong container for which analysis to run.
What is being tunedTuned byNot by
Which analysis an order receivesrecipe YAML — authored, reviewed, signed offa Skill
QC thresholds and checksQC spec, versioned with the recipea Skill
How a failure is diagnosedSkills — known errors, app guides, debug procedures—
How findings are wordedprompt templates—
What data may be sent wherethe allow-list in code, with the AI-usage policy as substratea Skill alone

Where Skills earn their place

  • Failure triage — load the known-error catalog, the app's developer guide and the debug procedure, then read logs, check gStore, query SLURM. Output is a proposal to a human, never an action
  • The verification discipline itself — declare the evidence spec first, compute a fail-closed verdict, record it with the spec hash. Our QC gate is an instance of it
  • Institutional guardrails as substrate — the AI-usage policy loads as a Skill, so every agent inherits it
  • Tuning without redeployment — improving triage means editing a Skill, not changing the daemon

The anti-pattern, and one caveat

  • Putting an analysis choice in a Skill — "for RNA-seq use STAR then FeatureCounts". It would work, and it would quietly undo the whole design
  • Behaviour would then depend on which Skill version an agent happened to load, and the run record would no longer explain itself
  • A Skill is a prompt with provenance. It improves consistency and makes behaviour attributable. It does not turn the agent's conclusions into evidence
  • That is why triage output is advisory, and why a mechanical verdict sits underneath it

Layer 0 · Data minimisation
Do not ask permission for data we never read
B-Fabric order record Has many fields — customer name, contacts, project title, sample names, free-text comments.
→
Field allow-list (fixed in code) Service Type · Sequencing Application · Species · Instrument · Library Protocol · sample count / layout
→
FGCZ local model On-premises inference. Nothing leaves the FGCZ network. No external cloud at all.

Three rules

  • Allow-list, not redaction — unlisted fields are never fetched, so a scrubber bug cannot leak them
  • On-prem model only — the "which tool for which data class" matrix disappears
  • No raw data, no free-text logs — QC sends numeric metrics; log text can carry paths and sample names

What the customer is told

  • No dialog. No checkbox. A plain statement:
  • "Experiment parameters will be processed by a local AI model."
  • Wording and placement still to be confirmed with the owner of customer-facing text
The caveat to keep: this works only while the payload stays inside the allow-list. The allow-list is a security boundary — enforced in code, reviewed when it changes.

Pipeline · Reuse
From B-Fabric to SLURM, through what already exists
B-Fabric DB polled every few minutes — "new data is available in gStore for order X"
→
omakase-core allow-list → recipe engine → proposal → timer. Own state DB. No DDL on the SUSHI schema.
→
SUSHI backend REST API POST a job with a project-scoped token
→
job_manager → SLURM → gStore unchanged, existing path

What the REST route buys us, for free

  • Project-scope enforcement from the token
  • The required_params gate — unresolved reference parameters can no longer reach SLURM
  • Per-sample fan-out and legacy-parity output columns
  • No code path by which the orchestrator can corrupt the shared production database

A recipe, in one line

  • Match predicate over allow-listed parameters
  • Ordered app chain with fully resolved parameters
  • QC spec, compute budget, autostart flag
  • Authored by a bioinformatician, versioned in git, recipe_id@version recorded on every run

Layer 3 · The gate
The only thing that happens on a timer

Plain 4 hours

An order finishing Friday 17:00 auto-starts at Fri 21:00
Nobody is watching. Nobody can veto.
A failure sits untouched until Monday.

4 business hours, with a floor

08:00–18:00 Mon–Fri, never before the next working day 10:00 → Mon 10:00
The real grace period is more than two working days.
The owner can veto or override on arrival.

Rules around the clock

  • Post the notice, read it back, and only then start counting
  • Low confidence, non-whitelisted recipe, or over budget → held, a human must release it
  • A failure never auto-retries. It notifies a human.
  • Global pause switch; opt-out per project, per customer, per recipe

Human actions, available on day one

  • List pending proposals with their deadline
  • Veto, override with a different analysis, or hold the clock
  • Read the QC report, then release the result to the customer
  • Works from the command line — no user interface needed for phase 1
Every other transition needs an event or a human. Exactly one transition in the whole system is driven by time.

Chat surface · Slack / Teams
A secretary for the veto window
The three channels so far answer "can a human act?". A bot answers a different question: will a human notice in time? That is the weakest point of the whole gate — an unread comment makes the veto window ceremonial.

What it posts

  • Every morning — proposals awaiting a response with their deadline countdown; jobs finished or failed since yesterday; QC warnings waiting for review
  • On a new proposal — order, recipe, resolved parameters, cost estimate, deadline, with veto and hold affordances
  • One hour before a deadline — a reminder naming the person expected to act
  • On demand — "status of order X", "what is pending for this project", "why did job 581 fail"

Two tiers — and the boundary is the governance boundary

  • Tier A, proactive — digests, alerts, deadline reminders. Plain code: query state, format, post. No LLM. Runs unattended because it is just a scheduled job
  • Tier B, reactive — free-text questions in a thread, answered by the agent with Skills, one task per message
  • A chat message is a human-initiated invocation — someone typed it and is watching the thread. So the conversational tier is attended by construction, which is what has blocked agentic use elsewhere
Constraints. Slack and Teams are external cloud services — the same classification question as the model, but about transport. Teams under the institutional tenancy is the safer default; Slack needs a policy check. The bot inherits the allow-list: post identifiers, states and deadlines, never sample names or result content. Chat identity must map to an LDAP login before it can act — phase 1: read, veto and hold from chat; override and release from the CLI.
Build order: an outgoing webhook posting the morning digest is about a day of work, has no inbound and no auth surface, and already delivers most of the value. Interactive buttons and the conversational tier come after the identity mapping exists.

Layer 5 · Quality control
The verdict comes from measurements, not from the model

Tier 1

Structural
  • Exit code
  • Expected outputs exist and are non-empty
  • Manifest parses; row count = sample count
  • No out-of-memory, no traceback
  • Runtime within a sane multiple of the median
absolute · cheap

Tier 2

Domain metrics
  • % uniquely mapped, % rRNA
  • Library-size distribution, duplication rate
  • Genes detected; barcode-rank knee for single cell
  • Species and design sanity checks
  • Thresholds versioned together with the recipe
per recipe

Tier 3

Historical comparison
  • Each metric compared against the last N runs of the same recipe
  • Outliers flagged even when every file is present and the job succeeded
  • This is what catches "the pipeline ran fine but the data is wrong"
the interesting one
The criteria are declared before the run and recorded with the result.
The model may downgrade a verdict. It may never upgrade a failure.

Plan · Phases
Nothing reaches a customer until the counters allow it

Phase 0 — Shadow

can start now · zero risk
  • Detect, propose, run QC — write nothing anywhere
  • Audit how usable the order metadata actually is, per service type
  • Bioinformaticians author recipes for the top order types
  • Compare proposals against what is actually run, on new orders
exit: recipes signed off

Phase 1 — Human-gated

the original phase 1
  • Internal notification only
  • Auto-start after the business-hours deadline, for whitelisted project × recipe pairs
  • Release to the customer always needs a human
  • The AI writes nothing customer-facing
exit: per-recipe counters

Phase 2 — AI to customer

per recipe, with sign-off
  • Only for recipes that passed the phase-1 criteria
  • Comment is AI-drafted and labelled as such
  • Warnings, failures and held proposals still go to a human
  • Pause switch and opt-out stay permanently
promotion is earned, not assumed

Customer text

  • Wording and placement of the local-AI-model notice; who signs it off
  • Must a phase-2 customer-facing comment state that it is AI-drafted? Our reading of the UZH / ETH transparency rules: yes

Operations

  • Confirm the grace period counts business hours
  • Pilot scope: which order types, which projects
  • Compute budget, monthly cap, and a low-priority queue so first-pass jobs never delay ordered work
  • What "forward the result" means concretely
One architectural decision to make now: LLM calls already exist in more than one place (the M&M module in ezRun, method-description generation in SAKE). A shared library is impossible across R, Ruby and Python — only a shared service is. Agreeing on one before the third caller exists is the cheap moment.
